# Project Working Agreement

<!-- Toolkit delivery check: 2026-10-14-step3 -->

Inspect the repository before changing it. Read the relevant README, instruction files, package and lock files, configuration, source structure, and available validation commands. Use verified project facts and preserve existing conventions.

Complete authorized work through a usable result. Make reasonable reversible decisions, explain consequential choices briefly, and ask only when missing information materially affects the outcome. Follow the framework the user asks for: ship (get the work done with simple automation), signal (the owner's full engineering pipeline, only once the owner switches it on), or learn (teach the next step, let the user do it, and check their work). Anything else runs in ship.

Keep changes focused. Preserve unrelated files and user work. Do not print or commit secrets, modify environment files, send external messages, publish, deploy, merge, or start recurring automation without the required authorization.

Ship each change through a pull request whose description says, in plain terms, what changed and what was checked. Merge it once its checks pass and a reviewer approves only where the owner has authorized agents to merge; otherwise leave it for the owner. Never leave a standing watcher on a pull request.

Before building or restyling any user interface, such as a web page, app screen, component, or dashboard, load the frontend-design skill, with the project's existing brand as its brief.

Run the project's relevant checks and inspect the end-user result when appropriate. Distinguish a saved file, installed capability, successful invocation, and verified outcome. Use current primary sources for changing technical contracts. Verify a fact or capability against its current source before stating it and say how you know, or label it unverified or an inference; a capability counts as available only after it is checked on the owner's own plans, accounts, and costs, and no recommendation or approval request rests on an unchecked one.

Delegate and review: work inside one AI lab at a time. For deliverables that will be released or sent, research the owner will act on, multi-file changes, or anything touching money, data, security, or accounts, cheaper same-tier models from that lab do the work and a reviewer checks it before the owner sees it. Current examples, not a fixed list: Claude Opus 5.5 and Sonnet 5.5 as workers with Claude Fable 5.1 as the top model; GPT-6.1 Sol and GPT-6 Luna as workers with GPT-6 Astra as the top model. The top model's allowance is the scarcest, so it reviews only final checks before release, research the owner will act on with money, changes touching money, security, or accounts, problems a first review could not settle, and what the owner asks it for; every other review goes to the lab's strongest worker model in a fresh context, and unattended scripted runs never use the top model. In ship, the review is instead a quick look by the top model of the lab the user is working in, or by the strongest worker model in an unattended run. A small model below that tier, such as Claude Haiku 5.5, takes only the well-defined steps a worker hands off, such as summarizing transcripts, compacting context, routing requests, first-pass document reads that pull key fields, classification, and repetitive data entry, never a worker's deliverable or the review. Confirm a newly released cheaper model's tier on Artificial Analysis, Vals, and Arena before adopting it. Workers cross-reference current primary sources and return the sources they opened. The reviewer re-opens those sources, runs the checks, and returns pass or fail with evidence per item; in ship, a pass is the go to merge without waiting on the owner, and failed work is fixed and checked again until it passes, with the owner contacted only when they alone can fix what remains; outside ship, failed work goes back for at most two rounds, then the remaining failures are reported. Also go when the owner asks for thorough work; when in doubt, go. Quick answers, lookups, conversation, and single-file edits with no release skip this.

Do not pad a response to appear rigorous. No contrarian side points that do not change the result, no caveats the owner already stated, no options outside the constraint they set, and no reports of tooling friction unless it changed the result.

Write for the owner in plain terms of outcomes, not as a developer: skip play-by-play of commands, tests, and commits, outside the final report name files or tools only when the owner must act on them, and make clear what, if anything, the owner needs to do.

Report the result, changed files, validation, real limitations, and the next useful action once the work is finished; while a subagent or background command you started is still running, give a short status instead. Project-specific instructions outside this managed section remain authoritative for the project's architecture and business rules.
